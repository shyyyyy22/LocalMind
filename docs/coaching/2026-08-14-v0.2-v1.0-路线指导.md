# V0.2 → V1.0 路线指导（2026-08-14）

> 前置：本指导默认 V0.1 已收尾（搜索模块 + pytest + FastAPI 基础 UI + 配置化）。
> 若 V0.1 未完成，先按 `2026-08-13-v0.1-剩余路线.md` 补完，再进入本路线。
>
> 定位：**边做边学**——每个版本先明确"要学什么"，再做功能。本文件只给方向与决策点，不给代码。

---

## 总览地图

| 版本 | 一句话目标 | 新增核心概念 | 主要新知识 |
|---|---|---|---|
| V0.2 | 能搜到**文件内容** | 文档解析、倒排索引 | 解析器接口、FTS5/分词 |
| V0.3 | 能按**意思**搜 | Embedding、向量检索 | 向量化、ANN、chunking |
| V0.4 | 搜索质量 + 能**回答** | 混合检索、重排、RAG | 融合算法、Cross-Encoder、Prompt |
| V0.5 | 自然语言**调用工具** | Tool Calling、Agent | 工具协议、规划循环 |
| V0.6 | 安全地**操作文件** | 受控操作、Undo | 操作事务、回滚设计 |
| V0.7 | 发现**文件关系** | 知识图谱 | 概念抽取、图模型 |
| V1.0 | 完整可用产品 | 集成、评测、部署 | 工程化、文档化 |

**每个版本都必须满足三条硬原则：独立可用、可测试、可评测。**

版本推进顺序：

```text
补完 V0.1
    ↓
V0.2 全文搜索 → V0.3 语义搜索 → V0.4 Hybrid RAG
    ↓
V0.5 Agent → V0.6 文件管理 Agent → V0.7 知识图谱 → V1.0
```

## V0.2 — 全文搜索（搜到内容）

### 目标

搜"注意力机制"能命中 `transformer_notes.md` 里的文字，而不只是文件名。

### 要学的知识

- **统一解析器接口**：`parse(file) -> Document`，PDF / Markdown / 代码 / Office 各自实现同一个接口（设计文档第 7 节）。学"接口抽象"这个思想——这是本项目第一次做抽象，V0.3 / V0.4 的 Provider 抽象是同一模式的复用
- **SQLite FTS5**：倒排索引的原理、`MATCH` 语法、BM25 排序
- **中文分词**：FTS5 默认 `unicode61` tokenizer 按空格/标点切词，**中文会整句连在一起导致搜不到**——这是本版本最大的坑

### 要做的功能（对应设计文档第 27 节 V0.2）

- 解析器：`.txt` / `.md` / `.py` / `.cpp` / `.h` / `.java` / `.json` / `.csv`（V1 范围，先做这些）
- 解析结果写入索引，支持内容关键词搜索
- 文件变更后重新解析、同步索引

### 要自己做的设计决策

1. 解析时机：扫描时就解析入库，还是搜索时才懒解析？（建议扫描时解析，watcher 事件驱动）
2. 解析后的文本存哪：新增 `documents` / `chunks` 表，还是直接建 FTS 表？
3. 中文搜索怎么解决：jieba 预分词 / FTS5 trigram / 分词辅助表——调研后选一个，并记录理由
4. 文件变了怎么办：watcher 的 `on_modified` → 重新解析 → 更新 FTS 索引（注意同步顺序）

### 坑

- 扫描型 PDF 需要 OCR，本阶段不做，记录为限制
- 大文件 / 二进制文件要跳过或截断
- 文本编码识别（GBK / UTF-8 / UTF-16）

### 验收标准

- `搜索"注意力机制"` 命中 `transformer_notes.md`
- `搜索"五子棋"` 命中 `gomoku.py` 的内容
- 修改文件后再次搜索，结果同步更新

## V0.3 — 语义搜索（按意思搜）

### 目标

搜"让 AI 自己玩游戏的方法"能找到 `gomoku.py` 和 RL 笔记——即使没有相同关键词。

### 要学的知识

- **Embedding 原理**：句子怎么变成向量、余弦相似度为什么能衡量语义接近
- **本地 embedding 模型**：中文场景调研 bge / m3e 这类中文友好的模型（设计文档推荐 Sentence Transformers）
- **ANN 向量检索**：FAISS 的 `IndexFlatIP`（精确）vs `IndexIVFFlat` / `HNSW`（近似）——学清楚"为什么需要近似检索"
- **Chunking 策略**：怎么切分文档（固定长度 / overlap / 按结构切）——为实验做准备
- **Provider 抽象**：EmbeddingProvider 接口，本地模型 vs API 模型可切换。**这是第一次引入抽象层，V0.4 的 LLMProvider 复用同样模式**

### 要做的功能（对应设计文档第 27 节 V0.3）

- 文档切块（chunk）并向量化
- 向量检索，语义搜索入口
- chunk → 文件的映射，结果能回溯到文件
- 文件变更后重新切块、重新向量化、更新索引

### 要自己做的设计决策

1. 用什么模型（考虑中文效果、模型大小、离线可用）
2. chunk 怎么切——**别拍脑袋**，设计成可对比实验的方案（对应 `experiments/chunking/`）
3. chunk_id → file_id 的映射关系存哪
4. 文件变化后的同步：旧 embedding 怎么失效、重新生成（**这是 V0.3 最核心的工程问题**）

### 坑

- FAISS 索引的持久化和增量更新（`IndexIVF` 增量支持差，`HNSW` 可以——调研后选）
- 模型下载体积与离线模式
- 空文件 / 小文件不产生 chunk

### 验收标准

- 语义查询命中意思相近但无关键词的文件
- **开始建评测**：准备 20~50 条测试 query，记录 Recall@K

## V0.4 — Hybrid RAG（搜索质量 + 能回答问题）

### 目标

问"我之前 PPO 笔记里提到 Actor-Critic 吗？" → 回答并给出**来源**（文件 + 行号 / 段落）。

### 要学的知识

- **融合算法**：RRF（Reciprocal Rank Fusion）和加权分数融合——为什么关键词和向量结果要融合
- **Reranker**：Cross-Encoder 为什么比 bi-encoder 重排更准；它和 embedding 的区别
- **RAG 全流程**：检索 → 拼上下文 → 生成 → 带引用。学"grounding"（接地）思想——怎么让 LLM 只基于检索到的内容回答、减少幻觉
- **LLMProvider 抽象**：Ollama 本地模型 vs API，复用 V0.3 的抽象模式
- **评测指标**：Faithfulness（回答是否忠于原文）、Answer Relevance、Citation Accuracy

### 要做的功能（对应设计文档第 27 节 V0.4）

- BM25 + 向量 + 元数据融合
- 重排器
- RAG 问答 + 引用来源
- 检索评测（Recall@K / MRR / NDCG）

### 要自己做的设计决策

1. BM25 / 向量 / 元数据的权重或融合方式——**必须通过实验确定**，不要固定 40/40/20
2. Top-K 取多少、上下文塞多长（token 限制）
3. 引用格式：chunk 级？段落级？怎么定位到行号
4. 幻觉控制：找不到答案时说"不知道"，而不是编造

### 坑

- 重排器增加延迟
- 中英混合内容的 embedding 与 reranker 不匹配
- 上下文截断

### 验收标准

- RAG 回答能给出可点击验证的来源
- `experiments/retrieval/` 里能对比"关键词 vs 向量 vs 混合 vs 混合+重排"的 Recall@K 数据

## V0.5 — Agent（自然语言调工具）

### 目标

说"总结这个文件夹里的所有学习资料" → Agent 自己决定调哪些工具完成。

### 要学的知识

- **Tool Calling 协议**：LLM 输出结构化调用（工具名 + 参数）→ 代码执行并返回结果 → 再喂回 LLM。学清楚这个循环
- **工具设计**：`search_files` / `semantic_search` / `read_file` / `summarize_folder` / `find_duplicates`——每个工具的入参、返回值、错误处理
- **规划（Planning）**：单步 vs 多步（ReAct：思考 → 行动 → 观察 → 再思考）
- 设计文档：Agent **前期自己实现，后期再上 LangGraph**——自己实现一次才能理解框架解决的是什么问题

### 要做的功能（对应设计文档第 27 节 V0.5）

- 工具定义与注册
- Agent 循环（调用 → 执行 → 返回 → 再调用）
- 只读工具集：搜索 / 读文件 / 摘要 / 找重复

### 要自己做的设计决策

1. 工具 schema 怎么定义（JSON Schema）
2. 循环控制：最大迭代次数、停止条件、超时
3. 多轮对话记忆放哪
4. **安全边界**：本版本工具**只读**（搜索 / 读 / 摘要），危险操作留给 V0.6——先别混进来

### 坑

- LLM 生成的工具调用经常格式错误（要做好容错重试）
- LLM 会幻想不存在的文件路径（工具要返回真实存在的路径并校验）
- **Prompt Injection**：文件内容里可能藏着"忽略之前的指令"这类攻击，搜索 / 读取工具返回的内容不能无脑信任——这是安全话题，值得专门学习

### 验收标准

一句话指令能完成多步任务（如"找出重复的 PDF 并总结它们分别是什么"）。

## V0.6 — 文件管理 Agent（安全操作）

### 目标

"把 Downloads 里的论文整理到论文文件夹" → 生成操作计划 → **用户确认** → 执行 → 可撤销。

### 要学的知识

- **Human-in-the-loop 流程**：Request → Plan → 风险检查 → Preview → Confirm → Execute（设计文档第 14 节）
- **操作日志与 Undo**：`operations` 表记录每个操作（类型 / 源 / 目标 / 状态），Undo = 执行逆操作（move 的逆操作就是 move 回去）
- **原子性**：一批操作里一个失败怎么办（全部回滚 / 部分成功并记录）

### 要做的功能（对应设计文档第 27 节 V0.6）

- move / rename / create_folder（delete 单独考虑）
- 操作预览与用户确认
- 操作日志 + Undo

### 要自己做的设计决策

1. 操作计划的数据结构（给用户展示什么：每个文件从哪到哪）
2. 风险分级：move / rename 低风险，delete 高风险——**delete 建议进回收站而不是直接删**
3. Undo 的边界：move / rename 可逆；delete 进回收站后怎么撤；操作进行中 watcher 事件怎么处理
4. **自触发问题（大坑）**：你自己的 move 会触发 watcher 的 `on_moved` → 数据库更新，这套联动逻辑要想清楚，否则重复处理或死循环

### 坑

- 跨磁盘移动 = 复制 + 删除而非重命名
- Windows 路径长度限制
- 权限错误的部分成功状态
- Undo 时目标已被占用

### 验收标准

一次整理操作从预览 → 确认 → 执行 → 撤销，全程有日志可查。

## V0.7 — 知识图谱（文件关系）

### 目标

搜"Transformer"显示相关文件（BERT.pdf、transformer.py）和相关概念（Attention、Encoder）。

### 要学的知识

- **图模型**：节点（File / Chunk / Concept / Project / Tag）+ 边（mentions / related / code）存哪、怎么查
- **概念抽取**：用 LLM 从 chunk 里抽概念，还是用现成 NLP 工具（spaCy 等）
- **关系推断**：共享概念 → 文件相关；代码 import → 代码相关

### 要做的功能（对应设计文档第 27 节 V0.7）

- File–Concept 两层节点 + mentions 边
- 概念抽取入库
- 相关文件 / 相关概念展示

### 要自己做的设计决策

1. 节点 / 边的类型定义（别贪多，先做 File–Concept 两层）
2. 构建时机：批量建 vs 增量更新（新文件入库时顺便抽概念）
3. 存储：SQLite 边表够不够（本规模足够，**不需要**图数据库——这也是个学习点：什么时候该上重型工具）

### 坑

- LLM 抽取概念不稳定（同一概念多种写法，需要归一化）
- 图谱构建慢（可以后台任务）

### 验收标准

搜索一个概念能看到"相关文件 + 相关概念"两个区块。

## 贯穿始终的三条纪律

1. **实验从 V0.3 就开始**：`experiments/` 不是最后补的——chunking 对比（V0.3）、检索对比（V0.4）都是边做边记录，最后才有真实数据
2. **评测数据集增量积累**：每做一个功能就往测试集里加几条 query，别最后一次性编 100 条
3. **抽象只在需要时引入**：V0.2 不需要 Provider 抽象；V0.3 引 EmbeddingProvider，V0.4 复用同一模式加 LLMProvider——过早抽象是学习陷阱，过晚重构是技术债

## 提前埋下、先别改的问题

> 同 V0.1 文档风格：这些问题"做到那个版本自然会遇到"，先别改，遇到时再解决。

1. **V0.2**：`scanner.py` 和 `watcher.py` 重复的建记录逻辑——做解析器时会被迫重构（先忍着）
2. **V0.3**：files 表缺 `mime_type` 和 `status` 字段——语义搜索要跳过哪些文件（如大二进制）时就会需要它
3. **V0.4**：chunk 和文件的关联必须能追溯到行号，否则 RAG 引用做不出来——V0.3 设计 chunk 表时就要留位置
4. **V0.5**：工具返回给 LLM 的内容要截断，否则上下文爆炸——提前想好每个工具的输出上限
5. **V0.6**：你自己的文件操作会触发 watcher——V0.1 的 watcher 从第一天起就要能区分"我改的"和"用户改的"

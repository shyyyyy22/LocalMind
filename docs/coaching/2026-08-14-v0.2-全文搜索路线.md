# V0.2 全文搜索 —— 路线指导

> 2026-08-14 ｜ 前置：V0.1（本地文件索引器）已完成 ✅

## 一、V0.2 要做什么

一句话：让 `search` 不仅能按元数据（文件名/路径/大小/时间）搜，还能按**文件内容**搜。

设计文档定义（第 1063 节）：

- PDF Parser
- Markdown Parser
- Code Parser
- Office Parser
- SQLite FTS5
- 文件内容搜索

## 二、整体架构：V0.2 在 V0.1 上加什么

```
scan 一条新文件时的数据流（V0.2 扩展部分加粗）：

  文件 → 元数据 → files 表（V0.1 已有）
       ↘ **解析内容 → file_content 表 → FTS5 索引（新增）**

search --content 时：

  **FTS5 MATCH → 按相关度排序的 file_id 列表 → join files 表 → 完整结果**
```

新增模块建议（包结构延续 V0.1 风格）：

- `app/parser/`：解析器包（统一接口 + 按扩展名分发到具体解析器）
- `app/database/models.py`：新增 `file_content` 表（`file_id` 外键关联 `files.id`）
- `app/search/search.py`：新增 `content` 参数（FTS 查询路径）
- `app/cli/__main__.py`：`search` 子命令新增 `--content` 选项

## 三、里程碑拆解（严格按依赖顺序）

设计文档第 25 节建议"第 4 周 PDF、第 5 周 FTS"，本指导把顺序调整为**先跑通流水线、再扩展覆盖面**，理由见每个里程碑的"为什么"。

---

### M1 解析器接口 + 纯文本解析器（txt / md / code）

**目标**：建立解析器体系，让 txt、md、代码类文件的内容进入数据库。

**学什么**

- 解析器统一接口的价值：多种文件格式 → 同一种抽象（如 `parse(path) -> str`）；按扩展名分发的注册表模式
- 编码问题：`open(path, encoding='utf-8', errors='ignore')` 的 `errors` 参数；Windows 上 GBK 编码文件读 UTF-8 会炸，怎么兜底
- `pathlib` 的 `suffix` 分发（V0.1 已用过，这里是复用）

**为什么**：纯文本类零第三方依赖，能最快把"解析 → 入库 → 查询"整条流水线打通；后面 Office/PDF 只是往注册表里加新解析器，骨架不动。

**验收标准**

- `scan --path` 后，`file_content` 表中 txt/md/code 文件有对应内容记录
- 空文件：内容为空串且不报错
- 编码异常的坏文件：不崩溃、不毒死整个扫描（记录状态/跳过，参考 V0.1 失败隔离）

---

### M2 FTS5 全文索引 + 内容搜索

**目标**：SQLite FTS5 建全文索引，`search --content` 可搜内容，按相关度排序。

**学什么**

- 倒排索引原理（FTS 的本质：词 → 文档 ID 列表，为什么它比 `LIKE '%x%'` 快几个数量级）
- FTS5 基本用法：`CREATE VIRTUAL TABLE ... USING fts5(content)`、`MATCH` 语法、`bm25()` 相关度排序函数
- SQLAlchemy 执行裸 SQL：FTS5 是 SQLite 扩展，ORM 模型不直接支持，要用 `session.execute(text(...))`
- FTS 结果如何 join 回 `files` 表拿完整元数据（rowid 对齐）

**为什么**：先用 FTS5 默认的 unicode61 tokenizer 跑通流程；中文分词问题留给 M6，不要让中文优化阻塞主流水线。

**验收标准**

- `python -m app.cli search --content <英文关键词>` 返回匹配文件，**按相关度降序**
- 多关键词（空格分隔）默认 AND 匹配
- 结果能 join 出完整元数据（复用 V0.1 的表格输出）
- `--limit` 对 FTS 路径同样生效
- `--content` 与 V0.1 元数据条件（`--ext`、`--path` 等）可组合过滤

---

### M3 Office 解析器（docx / xlsx / pptx）

**目标**：Office 新格式文件内容可搜。

**学什么**

- OOXML 的本质：docx/xlsx/pptx 都是 **zip 包 + 一堆 XML**——动手解压一个 docx 看看内部结构（这是本里程碑最有价值的一课）
- `python-docx`（docx）、`openpyxl`（xlsx）、`python-pptx`（pptx）各自的文本提取 API
- 为什么 `.doc` / `.xls` / `.ppt`（2003 及更早的二进制格式）**不支持**——解析器设计里"明确拒绝"比"静默失败"好

**为什么**：三个库都是纯 Python、安装即用；先学底层格式再学库，才知道库在替你做什么。

**验收标准**

- docx 段落文本、xlsx 单元格文本、pptx 幻灯片文本均可被 `--content` 搜到
- 遇到 .doc 等旧格式：明确跳过并提示"不支持"，不崩溃

---

### M4 PDF 解析器

**目标**：PDF 文件内容可搜。

**学什么**

- PDF 为什么难解析：PDF 是"排版指令的集合"而非文档结构——段落、顺序、表格边界都可能在提取时丢失
- `pypdf` 的 `extract_text()`；`pdfplumber` 能保留表格结构（本版本不必上，知道有这个东西即可）
- 文本层（text layer）概念：**扫描件 PDF 是图片，没有文本可提取**——如何识别并明确提示

**为什么**：PDF 是设计文档点名的第一个 Parser（第 25 节第 4 周），也是解析器里坑最深的；放在最后做，前面 M1–M3 的经验（失败隔离、接口抽象）都能直接复用。

**验收标准**

- 文本型 PDF 内容可被 `--content` 搜到
- 扫描件/无文本层 PDF：明确提示"无文本内容"，不崩溃

---

### M5 watcher 联动 + 增量更新

**目标**：文件增/删/改时，内容索引同步更新；scan 幂等扩展到内容。

**学什么**

- FTS5 表的 `UPDATE` / `DELETE` 命令（按 rowid）
- **external content 模式**：FTS 表只存索引、内容从 `file_content` 表读（rowid 对齐），避免内容存两遍；配套的同步触发器
- **hash 驱动的增量解析**（关键设计）：V0.1 已经算好 SHA-256——`scan` 时 hash 没变的文件**跳过内容重解析**。这是 V0.1 的 hash 第一次派上大用场

**为什么**：M2 先普通模式跑通，M5 升级 external content + 触发器；watcher 是 V0.1 已有模块，这一步是把两个版本真正接起来。

**验收标准**

- `watch` 运行中：新增文件 → 内容自动入索引；修改文件 → 索引更新；删除文件 → 索引移除
- 重跑 `scan`：hash 未变的文件不重解析（可用日志验证），已删文件内容索引被清理
- `watch` 后紧接着 `search --content`，新文件立即可搜

---

### M6（挑战，可选）中文搜索优化

**目标**：中文内容能按词/子串搜到。

**学什么**

- tokenizer 概念；unicode61 对中文的行为（整句连写的中文被当成一个 token → 搜中间词搜不到）
- SQLite 3.34+ 的 **trigram tokenizer**：三字符窗口索引，对中文子串匹配实用（先查你本机 SQLite 版本）
- 可选进阶：jieba 分词 + 自定义 tokenizer 方案

**为什么**：中文是用户的真实场景，但分词是独立的大课题；放在主线之后单独攻，不阻塞 V0.2 交付。

**验收标准**

- 中文文档内容，输入任意关键词（哪怕只是句子中间的一个词）都能搜到

---

## 四、关键设计决策（开工前想清楚）

1. **hash 驱动的增量解析**：解析是 V0.2 最重的操作（尤其 PDF/Office），绝不无脑全量重解析。V0.1 的 SHA-256 就是为此准备的。
2. **解析失败隔离**：坏文件/密码 PDF/编码异常的 txt，都不该中断整个 scan。延续 V0.1"单文件失败不影响整体"的原则。
3. **FTS 与元数据的关系**：FTS 负责"内容命中了哪些文件"，元数据过滤在其结果之上叠加——职责分离，`search` 函数保持可组合。
4. **内容存两份还是存一份**：M2 允许普通 FTS 表（内容复制进 FTS），M5 升级 external content（FTS 只存索引）——这是渐进式升级路线，别在 M2 就上最复杂的方案。
